# Архитектура

```text
Доверенный клиент / будущий интерфейс
  → API key, CORS, Host, лимит тела запроса
  → FastAPI /api/v1
      → проверка и нормализация → локальное хранилище
      → одна транзакция: image_assets + processing_jobs(pending)
  → worker (отдельный процесс в Compose)
      → короткий SELECT FOR UPDATE SKIP LOCKED
      → lease_token, lease_expires_at, attempts
      → VisionProvider.analyze вне транзакции
      → новый файл разметки
      → блокировка изображения + проверка актуальности lease
      → одна транзакция: detections + ссылка разметки + completed
  → JSON/CSV и защищённая выдача изображений
```

`app/api/routes` содержит HTTP-адаптеры, `app/schemas` — контракты, `app/services` — хранение, обработку, разметку и экспорт, `app/services/vision` — заменяемое распознавание. `app/db` хранит модели и фабрику сессий; изменения схемы живут в Alembic.

## Слой распознавания

`VisionProvider` остался единственной точкой подключения; добавился третий провайдер.

```text
app/services/vision/
  base.py              абстракция VisionProvider (без изменений)
  factory.py           mock | openai_compatible | local
  mock.py              пустой результат для проверки цепочки
  openai_compatible.py внешний мультимодальный сервер
  local_provider.py    адаптер локального пайплайна + ограничение конкурентности
  local/
    model_registry.py  URL, SHA-256 и лицензия каждого артефакта
    runtime.py         жизненный цикл ONNX-сессий: одна загрузка на процесс
    vehicle.py         этап 1 — RT-DETRv2, техника
    reference_gallery.py этап 1b — тип техники поиском по эталонным фото (DINOv2)
    plate_detect.py    этап 2 — YOLOv9 по тайлам в исходном разрешении
    geometry.py        этап 3 — четыре угла номера и гомография
    plate_ocr.py       этап 4 — два OCR-движка, ранжирование вариантов
    plate_format.py    грамматика казахстанских номеров (только проверка)
    attributes.py      этап 5 — производитель по надписи на технике
    pipeline.py        оркестрация этапов → VisionImageResult
```

Тяжёлые зависимости (`onnxruntime`, `opencv`, OCR-модели) импортируются лениво, внутри
`factory.get_vision_provider`. Режимы `mock` и `openai_compatible` работают без них, и
сервис поднимается, даже если CV-стек не установлен.

Модели загружаются **один раз на процесс** через `runtime.get_or_create` под блокировкой.
Пиковую память ограничивает не число моделей, а `VISION_MAX_PARALLEL_IMAGES`: сессии
общие, промежуточные тензоры — нет. Сам вызов пайплайна уходит в `asyncio.to_thread`,
поэтому event loop не блокируется. Worker прогревает модели при старте: отсутствующий или
повреждённый файл весов падает сразу и с понятным текстом, а не через минуты в виде
загадочной ошибки задания.

Тип техники решается тремя источниками по убыванию специфичности: галерея эталонов →
надпись на машине → класс детектора. Выбранный источник записывается в
`vehicle_type_source`, поэтому `tractor` от совпадения с эталоном отличим от догадки по
COCO-классу `truck`. Индекс эталонов загружается один раз на процесс, как и модели.

Каждый этап хранит собственную уверенность. `detections` получила отдельные координаты
номера, четыре угла, `vehicle_confidence`, `plate_detection_confidence` и
`plate_ocr_confidence` (миграция `0003`). Все новые колонки nullable и без server default,
поэтому строки, записанные прежними провайдерами, остаются валидными, а `confidence`
сохранил прежний смысл ради совместимости API.

Фрагменты номера до и после выпрямления лежат в `storage/plates` и удаляются **после**
успешного COMMIT — как и файлы разметки. Разрыв между COMMIT и удалением оставляет сирот,
которые подбирает сборщик мусора из `docs/OPERATIONS.md`.

PostgreSQL одновременно служит БД и постоянной очередью. Для масштаба одного сервиса отдельный Redis/RabbitMQ не требуется. Частичный уникальный индекс гарантирует не больше одного активного задания на изображение. PostgreSQL блокирует конкурирующие ручные правки и повторную обработку через строку изображения. Worker не держит соединение во время запроса модели.

Файл разметки имеет уникальное имя для каждой публикации. Старый worker с истёкшим lease не может заменить текущие объекты и ссылку на файл. При отмене процесса lease остаётся для восстановления. Сетевой сбой во время COMMIT может оставить его исход неизвестным, поэтому потенциально опубликованный файл не удаляется до сверки с БД в обслуживании.

При завершении успешного задания обновляются текущие объекты изображения. Ошибка провайдера не удаляет предыдущий успешный результат. Экспорт использует REPEATABLE READ для согласованности метаданных, объектов и заданий одного HTTP-запроса.

Хранилище общее для API и worker через Docker volume. Несколько worker-процессов допускаются; несколько машин потребуют общего POSIX-хранилища либо отдельного S3-адаптера. Ресурсы нормализации и распознавания ограничены конкурентностью и размерами файлов. Текущая конфигурация рассчитана на одну доверенную команду; многопользовательскую авторизацию и tenant isolation следует добавить вместе с публичным интерфейсом.
