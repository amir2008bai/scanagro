# Запуск и обслуживание

## Развёртывание

1. Создайте `.env` через `python scripts/init_config.py`. По умолчанию включён провайдер `local` — распознавание на открытых моделях без внешнего endpoint.
2. Установите `APP_ENV=production`, длинный случайный `API_KEY`, реальные `ALLOWED_HOSTS` и `CORS_ORIGINS`. Production-конфигурация с mock, коротким ключом или wildcard отклоняется при старте.
3. Выполните `docker compose up --build -d`, проверьте `docker compose ps` и `/api/v1/health`.
4. Для доступа извне поставьте HTTPS reverse proxy перед loopback-портом API. Ограничьте размер тела до 100 MiB или своего `MAX_REQUEST_MB`, частоту запросов, время чтения тела и число соединений. Пример для nginx — `deploy/nginx.conf.example`; замените имя домена и пути сертификатов.
5. Следите за диском, числом pending/failed jobs, возрастом processing jobs, HTTP 5xx и задержкой провайдера. `/health` проверяет схему БД и запись в хранилище; он не подтверждает доступность модели или качество распознавания.

Docker API/worker работают под UID/GID 10001, с read-only root filesystem, временным `/tmp` и общим writable volume. Для собственного bind mount заранее дайте UID 10001 доступ к каталогу. БД в Compose не публикуется наружу. Для удалённой БД используйте TLS и отдельные учётные данные с минимально необходимыми правами. Ключ провайдера и ключ API — разные секреты. Переключение ключей требует пересоздания процессов.

### Модели распознавания

Веса живут в томе `model_cache` (`/data/models` внутри контейнера) и **не встроены в образ**:
они большие и версионируются отдельно от кода. Сервис `fetch-models` скачивает их при
первом запуске и сверяет SHA-256 из `app/services/vision/local/model_registry.py`; `api` и
`worker` стартуют только после его успешного завершения. Нужен исходящий HTTPS — только в
первый раз.

```bash
# проверить, что всё на месте, не скачивая заново
docker compose run --rm fetch-models python scripts/fetch_models.py --dir /data/models --check-only
```

Чтобы собрать полностью автономный образ, раскомментируйте `RUN python scripts/fetch_models.py`
в `Dockerfile`. Обновление весов: измените запись в реестре вместе с новой контрольной
суммой, затем `docker compose run --rm fetch-models`. Несовпадение контрольной суммы — это
отказ, а не предупреждение: подменённые или недокачанные веса не должны молча ухудшать
распознавание.

Ресурсы: `worker` с провайдером `local` занимает ~0.6–1.0 ГБ RSS в установившемся режиме,
`mem_limit` задан 3 ГБ. Масштабируйте числом процессов worker, а не ростом
`VISION_MAX_PARALLEL_IMAGES`: сессии ONNX общие на процесс, промежуточные тензоры — нет,
и поднимать оба значения нужно вместе. Одна фотография 2688×1520 обрабатывается 5–19 с на CPU
(в среднем 8–9); `VISION_USE_PPOCR=false` ускоряет примерно втрое ценой измеримого падения точности.

### Галерея эталонов

Тип техники определяется поиском по эталонным фотографиям: в COCO нет класса сельхозтехники.
Эталоны лежат в томе `reference_gallery` (`/data/reference` внутри контейнера). Сервис
`fetch-models` при первом старте копирует туда комплект из образа (`reference_seed`) и
строит индекс; **уже существующие файлы он не трогает** — это ваши фотографии, а не наши.

```bash
# что сейчас в галерее
docker compose run --rm fetch-models python scripts/build_reference_gallery.py     --dir /data/reference --report

# после добавления фотографий — переиндексировать и перезапустить worker
docker compose run --rm fetch-models python scripts/build_reference_gallery.py --dir /data/reference
docker compose restart worker api
```

Индекс читается один раз при старте процесса, поэтому после пересборки нужен перезапуск.
Пустая галерея — допустимое состояние: этап отключается, остаётся грубая метка детектора.

Следите за долей `vehicle_type_source='detector'` в экспорте: её рост означает, что на
площадке появилась техника, которой в галерее нет. Это сигнал добавить фотографии, а не
менять пороги. Подробности — в `docs/REFERENCE_GALLERY.md`.

Фрагменты номеров до и после выравнивания копятся в `storage/plates`. Они растут вместе с
числом обработанных фотографий; `VISION_SAVE_PLATE_CROPS=false` отключает их сохранение, а
`scripts/cleanup_storage.py` убирает осиротевшие файлы наравне с разметкой.

Рекомендуемые начальные значения: `WORKER_CONCURRENCY=2`, `MAX_IMAGE_PIXELS=40000000`, `MAX_UPLOAD_FILES=25`, `MAX_UPLOAD_MB=25`. Проверенный комплект фотографий — 2688×1520; это проверка корректности, а не нагрузочный benchmark. Подбирайте RAM и лимиты под свои изображения и модель. `VISION_STORE_RAW_RESPONSE=false` минимизирует сохранение ответа внешней модели. Фотографии и номера передаются именно настроенному вами провайдеру.

## Обновление старого проекта

Остановите приём загрузок и старый API/worker. Сохраните дамп БД и хранилище. Примените миграции один раз, затем запустите новый API и worker. Не запускайте старые in-process задачи одновременно с миграцией `0002`.

```bash
docker compose stop api worker
docker compose run --rm migrate
docker compose up -d api worker
```

Миграции `0003` и `0004` только добавляют колонки: все они nullable и без server default, поэтому
строки, записанные прежними провайдерами, остаются валидными, а `confidence` сохраняет
прежний смысл. `vehicle_confidence` заполняется из `confidence` для существующих строк.
Откат `downgrade 0002` удаляет добавленные колонки вместе с данными о геометрии номера.

Миграция `0002` переводит старые processing jobs в pending, завершает лишние дублирующиеся активные задания, добавляет lease, индекс и ограничения. Старые результаты и изображения сохраняются. Если старая БД содержит некорректные bbox, миграция откатится: исправьте данные после проверки дампа, а не удаляйте таблицы. `alembic check` позволяет проверить соответствие моделей миграциям.

В исходном Compose изображения лежали в bind mount `./data`. Новый Compose использует volume. При обновлении существующей установки сохраните старый каталог и замените mount `image_storage:/data/storage` на `./data:/data/storage` либо перенесите весь каталог в volume с сохранением структуры `uploads/` и `annotated/`. Без этого ссылки старой БД будут вести к отсутствующим файлам.

## Резервное копирование

Для согласованной копии приостановите загрузки и API/worker. Делайте резервную копию БД и **всего** хранилища как одной версии. Пример для POSIX shell:

```bash
mkdir -p backups
docker compose stop api worker
docker compose exec -T db pg_dump -U app -d fable -Fc > backups/fable.dump
docker compose run --rm --no-deps -v "$(pwd)/backups:/backup" api \
  tar -czf /backup/images.tar.gz -C /data/storage .
docker compose start api worker
```

Каталог backups должен быть доступен UID 10001. Для Windows PowerShell не используйте перенаправление бинарного дампа в старых версиях shell: создайте дамп внутри контейнера `pg_dump -U app -d fable -Fc -f /tmp/fable.dump`, затем `docker compose cp db:/tmp/fable.dump ./backups/fable.dump`. Восстановление выполняйте сначала на отдельной проверочной БД командой `pg_restore` и в отдельном каталоге изображений; переключайте сервис после проверки совпадения ссылок и файлов. Не удаляйте рабочие данные до проверки восстановления.

## Сиротские файлы

После аварии между записью файла и COMMIT могут оставаться файлы без записи в БД. Это безопаснее, чем удалить файл при неизвестном результате COMMIT. Обслуживание нужно выполнять при остановленных API и worker; сборщик также игнорирует файлы моложе 24 часов.

```bash
docker compose stop api worker
docker compose run --rm --no-deps api python -m scripts.cleanup_storage
# Проверьте список. Только после проверки:
docker compose run --rm --no-deps api python -m scripts.cleanup_storage --apply
docker compose start api worker
```

Сначала выполняется dry run. Сборщик не удаляет файлы, на которые ссылается БД. После ручного удаления или переноса хранилища восстановите его из резервной копии; health проверяет доступность хранилища, а не существование каждого исторического файла.
