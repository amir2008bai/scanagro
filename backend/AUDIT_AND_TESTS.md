# Проверка и исправления бэкенда

Документ описывает два этапа. Первый — исправление исходного бэкенда. Второй — подключение
настоящего распознавания на открытых моделях; он описан в разделе
[«Этап 2»](#этап-2-локальное-распознавание) ниже, а метрики — в [RESULTS.md](RESULTS.md) и
[docs/RECOGNITION.md](docs/RECOGNITION.md).

## Этап 1 — исправление бэкенда

Проверен весь исходный архив fable_backend_ready.zip: Python-модули, маршруты API, схемы, SQLAlchemy-модели, обе конфигурации запуска, миграции, обработка изображений, экспорт и CLI. Исходная структура проекта сохранена. Задание из DOCX использовано как описание функций сервиса: техника, номера, тип, производитель/модель, JSON/CSV и разметка.

## Что исправлено

| Исходная проблема | Исправление |
| --- | --- |
| fire-and-forget `asyncio.create_task` терял задания при сбое | Постоянная очередь PostgreSQL, отдельный worker, lease и ограниченное восстановление |
| Параллельная обработка одного фото могла затереть результаты | Уникальный индекс активного задания, блокировки, токен актуальности публикации |
| Обработка создавала зависимость HTTP API от длительной операции модели | Модель вызывается вне транзакции, CPU/файловые операции вынесены из event loop |
| Частично успешная пакетная загрузка оставляла несогласованные данные | Предварительная валидация всех файлов, одна транзакция изображений и заданий |
| Недостаточная защита файлов и декодирования | Лимиты запроса/файлов/пикселей, MIME sniffing, полное декодирование, запрет анимации, проверка путей |
| EXIF-поворот расходился с координатами | Единая нормализованная копия для модели и разметки; удаление GPS и прочих метаданных |
| Правки и удаления объектов не меняли JPEG | Перегенерация разметки с атомарной публикацией и сохранением прежнего результата при сбое |
| `null` в обязательных PATCH-полях приводил к ошибкам БД | Проверка входных схем, согласованности номера и флага, валидируемый bbox |
| Пустой/некорректный JSON модели считался успехом или плохо обрабатывался | Обязательный список detections, проверка ответа, пустых choices, усечения и размеров |
| Повторы запросов провайдеру шли без пауз и без различения причин | Ограниченный backoff только для временных ошибок; безопасные диагностические сообщения |
| Ошибки распознавания путались с отсутствием объектов | Статусы, модель, provider и `is_mock` в экспорте |
| Экспорт читал все данные без лимита и допускал формулы в CSV | Фильтры/пагинация, ограниченный размер, согласованный снимок БД и нейтрализация формул |
| API был открыт, CORS разрешал любые origins | Проверка ключа до разбора multipart, явные hosts/origins и проверка production-конфигурации |
| Контейнер работал как root, миграции запускались в каждом API | UID 10001, read-only filesystem, отдельный сервис миграции, постоянные тома |
| CLI выгружал чужие изображения и не сохранял разметку | Экспорт только текущего запуска, скачивание JPEG, manifest, resume, тайм-аут и ненулевой код при ошибках |
| Неоднозначный COMMIT мог вызвать удаление уже опубликованного файла | Сохранение спорных файлов до сверки с БД; отдельный dry-run сборщик сирот |

## Выполненная проверка

- **57 автоматических тестов**: схемы, настройки, storage, OpenAI-compatible HTTP-контракт, API, PostgreSQL, очередь, конкурентные захваты, устаревший worker, тайм-ауты, исправления, удаления, экспорт, лимиты и миграция старых данных.
- PostgreSQL 16 в отдельном контейнере: миграция с нуля; соответствие моделей `alembic check`; обновление схемы 0001 с дублирующими pending/processing jobs и неконсистентным флагом номера, с сохранением исходной записи изображения.
- Docker Compose: успешная сборка и запуск БД, migrate, API и worker. API health — healthy; пользователь процесса — UID/GID 10001; `pip check` без конфликтов.
- Перезапуск работающего API при остановленном worker: pending job сохранился; после старта worker завершился успешно.
- Все 25 фотографий пользователя прошли настоящий HTTP API и отдельный Docker worker в режиме mock. Завершено 25/25, ошибок 0; выгружено 25 JPEG, проверены декодирование и размеры. Повтор `--resume` не создал дубликатов.
- `ruff check`, `ruff format --check`, компиляция Python. Закреплённые runtime-зависимости проверены `pip-audit`: известных уязвимостей на дату проверки 17 сентября 2026 не обнаружено. Это проверка Python-зависимостей, а не аудит всех пакетов ОС контейнера.

## Как повторить тесты

```bash
python -m pip install -r requirements-dev.txt
python -m ruff check app scripts tests migrations
python -m ruff format --check app scripts tests migrations
python -m pytest -q
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Чтобы запустить все тесты, выделите отдельную PostgreSQL БД с именем, оканчивающимся на `_test`, и задайте `TEST_DATABASE_URL=postgresql+asyncpg://USER:PASSWORD@localhost:5432/fable_test`. **Её таблицы очищаются тестами, а тест миграций меняет схему. Никогда не используйте рабочую БД.** Тесты не берут URL рабочей БД из `.env` и не вызывают реальную модель.

В `.github/workflows/ci.yml` подготовлена такая же проверка в Linux с PostgreSQL. Сам workflow в GitHub не запускался, поскольку репозиторий не публиковался.

## Этап 2 — локальное распознавание

Подключено настоящее распознавание на открытых моделях, без платного API и без внешнего
endpoint. Архитектура сохранена: распознавание подключено через существующий слой
`VisionProvider` как третий провайдер `local`, режимы `mock` и `openai_compatible` работают
без изменений.

| Требование задания | Что сделано |
| --- | --- |
| Найти всю видимую технику | RT-DETRv2 R18 (Apache-2.0) на 960², COCO-классы отображены на наш словарь, исходный класс сохранён в `source_label` |
| Определить тип техники | Поиск по галерее эталонных фотографий (DINOv2, Apache-2.0) плюс уточнение по надписи и грубый класс детектора как запасной вариант. В COCO нет класса сельхозтехники: детектор сам по себе верен на 6/24 кадров, с эталонами — 20/24 |
| Найти номер и связать с машиной | YOLOv9 (MIT) по тайлам в исходном разрешении; номер привязывается к наименьшей рамке, которая содержит его центр |
| Прочитать номер | Два OCR-движка (MIT + Apache-2.0) по четырём вариантам фрагмента, ранжирование по измеренной уверенности |
| Производитель и модель, когда подтверждается изображением | Чтение надписей на технике; при отсутствии или неоднозначности — `null` |
| Сохранить в БД, JSON/CSV, разметка | Миграция `0003`, новые поля в экспорте, рамки техники и номера разными цветами |

### Что добавлено к проверке

- **112 автоматических тестов** (было 57). Новые: грамматика номеров и её отказ достраивать
  символы, геометрия на синтетических номерах с известными углами, разделение координат
  и уверенностей техники и номера, отображение на колонки БД, отказ от неоднозначного
  бренда, привязка номера к правильной машине.
- **Миграция `0003`**: проверены `upgrade head`, `downgrade 0002`, повторный `upgrade`,
  `downgrade base` и полный `upgrade` с нуля на PostgreSQL 16. Все новые колонки nullable
  без server default, `vehicle_confidence` заполняется из `confidence` для прежних строк.
- **Реальный прогон 25 фотографий** через HTTP API и отдельный Docker worker в режиме
  `local`: завершено 25/25, ошибок 0, `is_mock=false`, provider `local`. Обнаружено 38
  объектов техники и 21 номер, из них 7 приняты как прочитанные, сохранено 40 фрагментов
  номеров до и после выравнивания. Это настоящее распознавание, а не заранее записанные
  ответы. Результаты совпали с локальным прогоном `eval/evaluate.py`.
- **Docker**: образ собирается и запускается; `db`, `migrate`, `fetch-models`, `api`,
  `worker` отрабатывают по цепочке зависимостей. `fetch-models` скачал 5 артефактов и
  сверил SHA-256 внутри контейнера; `api` — healthy; процессы под UID/GID 10001 с
  read-only rootfs. Веса загружаются по явному пути из тома, а не из `~/.cache`, которого
  в контейнере нет.
- **`ruff check`, `ruff format --check`, `alembic check`** — без замечаний. `alembic check`
  поймал расхождение индексов между моделью и миграцией `0003`; исправлено.
- **Измерение на размеченной выборке**: `eval/ground_truth.json` + `eval/evaluate.py`.
  Разметка сделана вручную по исходным фотографиям и разделена на читаемые, частично
  читаемые и нечитаемые кадры; знаменатель метрик указан явно.
- **Сравнение вариантов выравнивания**: `eval/perspective_report.py` сохраняет фрагменты до
  и после исправления перспективы и таблицу всех чтений с уверенностями.

| Корректный отказ на частично читаемых | 8 / 8 |
| Ложных срабатываний на нечитаемых | 0 / 10 |

кадры. Разбор каждой ошибки и каждого отказа — в [RESULTS.md](RESULTS.md).

## Границы результата

Распознавание работает локально на открытых весах, но качество измерено только на 25 кадрах
одной камеры одного объекта. Это не оценка обобщения. Дообучения на этих кадрах не было,
однако пороги выбирались по ним, поэтому числа следует считать проверкой на вменяемость, а
не результатом на отложенной выборке. Сельхозтехника (тракторы, «Кировец», МТЗ) в выборке не
даёт ни одного читаемого номера, поэтому путь чтения номеров спецтехники практически не
проверен. Двухстрочные номера приняты как предварительные: порядок строк восстановлен по
кадрам, а не по опубликованному стандарту. Кириллица не читается, что ограничивает
определение производителя. GPU не тестировался. Для допуска в эксплуатацию остаются проверка
на большей размеченной выборке и настройка домена, HTTPS, секретов, резервного копирования и
ресурсов сервера. Предусмотрена конфигурация для этого; удалённая инфраструктура не
развёртывалась.

Сервис рассчитан на одну доверенную команду. Пользовательские аккаунты, роли, tenant isolation и S3 не добавлялись без требований; точки расширения и ограничения описаны в документации.
