# Что изменилось в этом пакете

Подключено **настоящее распознавание на открытых моделях**, локально, без платного API и
без внешнего endpoint. Прежняя архитектура сохранена: распознавание добавлено как третий
провайдер `local` через существующий слой `VisionProvider`, режимы `mock` и
`openai_compatible` работают без изменений. Проект не переписывался.

## Быстрый запуск

```bash
cd backend
python scripts/init_config.py
docker compose up --build -d
```

Сервис `fetch-models` при первом старте скачает веса (~212 МБ) и сверит SHA-256; `api` и
`worker` дождутся его успешного завершения. Нужен исходящий HTTPS — только в первый раз.
GPU не требуется: **2 ядра CPU и 2 ГБ RAM** для worker.

Обработать папку с фотографиями:

```bash
python scripts/process_directory.py ../photos --out my_results
```

## Интерфейс проверки

После `docker compose up` откройте **http://localhost:8000/ui/** и введите `API_KEY` из
`.env`. Это статические HTML/CSS/JS на 41 КБ без зависимостей: нет npm, нет сборки, нет
второго порта, нет настройки CORS — страницу отдаёт сам API.

Что он показывает и почему именно это:

- сетку с миниатюрами (отдельный кэширующий эндпоинт: 31 КБ вместо 2.4 МБ на кадр);
- по клику — исходный кадр с интерактивными слоями: рамка техники, рамка номера, четыре
  угла номера, подписи. Слои включаются и выключаются;
- **отказы наравне с ответами.** Непринятый номер обведён янтарным, рядом сырое чтение и
  причина отказа. Тип, взятый из класса COCO, помечен как догадка с пояснением, что делать.
  Обычная демонстрация такое прячет — здесь это главное, что нужно видеть при проверке;
- фрагменты номера **до и после исправления перспективы** рядом друг с другом;
- три уверенности раздельно: техника, рамка номера, чтение номера;
- правку номера и типа прямо из карточки; после правки `vehicle_type_source` становится
  `manual`, а машинная оценка уверенности снимается — значение пришло от человека;
- фильтры: прочитано / отклонено / без номера / тип-догадка / ошибки, и поиск по номеру.

Ключ лежит в `localStorage` и уходит только в ваш же API. Страница отдаётся без ключа —
в ней нет секретов; всё под `/api/v1` ключ по-прежнему требует, и на это есть тесты.

## Результат на 25 присланных фотографиях

| Метрика | Значение |
| --- | --- |
| Номер локализован там, где он виден человеку | 15 / 15 |
| Точное совпадение на полностью читаемых кадрах | **7 / 7** |
| Ошибок символов на них | 0 |
| Корректный отказ на частично читаемых | 8 / 8 |
| Ложных срабатываний на нечитаемых | 0 / 10 |
| Производитель верно / неверно | 3 / 0 |
| **Тип техники: детектор сам по себе** | 6 / 24 |
| **Тип техники: галерея эталонов** | **20 / 24** (1 ошибка, 3 отказа) |
| Секунд на кадр, CPU | 5–19, в среднем 8–9 |

**Это 7 полностью читаемых номеров с одной камеры одного объекта.** Универсальную точность
такая выборка не доказывает: она показывает поведение на этой камере и ловит регрессии.
Дообучения на этих кадрах не было, но пороги подбирались, глядя на них. Разбор каждого
отказа — в `RESULTS.md`.

Ключевое свойство: номер объявляется прочитанным **только при совпадении с известным
форматом Казахстана**. Уверенное, но структурно невозможное чтение (`597AQ10` — две буквы
там, где формат требует три; метка времени камеры) сохраняется в `plate_text_raw` с
причиной отказа, а `license_plate` остаётся пустым. Символы никогда не достраиваются.

## Тип техники по эталонам

В COCO нет класса сельхозтехники, поэтому «Кировец» и МТЗ приходили от детектора как
`truck`. Добавлен этап поиска по галерее эталонных фотографий: DINOv2 кодирует каждый
эталон один раз, кроп техники сравнивается по косинусной близости, и тип принимается
только при достаточной близости **и** достаточном отрыве от второго класса. Иначе — честный
отказ и грубая метка детектора, а поле `vehicle_type_source` показывает, что именно решило.

Эталоны добавляются папками, переобучения нет:

```bash
python scripts/seed_reference_from_frames.py --photos /путь/к/кадрам --labels мои_метки.json --source site_archive
python scripts/build_reference_gallery.py
```

**Что реально помогает.** Измерено на этих кадрах:

| Галерея | Верно | Ошибок | Отказов |
| --- | --- | --- | --- |
| Детектор сам по себе | 6 / 24 | — | — |
| Кадры с вашей площадки (24 эталона) | **20 / 24** | 1 | 3 |
| Площадка + веб (72 эталона) | 20 / 24 | 1 | 3 |
| Только веб-фото (48 эталонов) | 6 / 24 | 4 | 14 |

**48 свободно лицензированных каталожных фото классифицируют эту съёмку не лучше, чем
COCO, и ничего не добавляют поверх кадров с площадки.** Разрыв доменов реален: каталожные
снимки сбоку при хорошем свете против фишай-камеры сверху через пыль. Они оставлены только
ради классов `combine_harvester` и `wheel_loader`, которых в 25 кадрах нет вовсе.

Вывод простой: **нужен ваш архив с этой камеры**, особенно виды сзади — все четыре промаха
именно там, где кузов бортового ГАЗа неотличим от прицепа. Подробности, лицензии и
атрибуция — в `backend/docs/REFERENCE_GALLERY.md`.

## Что осталось незакрытым

- Сельхозтехника в выборке не даёт ни одного читаемого номера — путь чтения номеров
  спецтехники практически не проверен.
- Двухстрочные номера приняты как предварительные: порядок строк восстановлен по кадрам, а
  не по опубликованному стандарту.
- Кириллица не читается — это ограничивает определение производителя, но не чтение номеров
  (казахстанские номера латинские).
- GPU не тестировался; заявлен только CPU-режим.
- Марку по силуэту эталоны не определяют: МАЗ и КамАЗ одинаково близки (0.91). Марка
  остаётся за чтением надписи.
- Виды сзади: бортовой кузов и прицеп разделяются плохо; нужны эталоны именно этих ракурсов.
- Галерея в поставке собрана из тех же 25 кадров. Метрика считана с исключением кадра из
  индекса, но это всё равно не оценка на невиданной технике.
